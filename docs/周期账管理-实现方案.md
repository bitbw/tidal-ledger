# 周期账管理实现方案

> 版本：v1.0｜日期：2026-08-28
> 参考：挖财“周期账管理 / 周期账详情 / 编辑周期账 / 选择重复周期”截图，以及当前潮汐账本的 Neon、Drizzle、分类和流水实现。
> 目标：让用户为固定收入或支出建立周期规则，例如“每月 15 日 17:04 记一笔房租 2,800 元”，系统在到期时稳定生成一笔真实流水，并支持查看、编辑、结束和归档。

## 1. 产品范围与核心规则

### 1.1 首期支持范围

| 能力 | 首期行为 |
| --- | --- |
| 收入 / 支出 | 支持；继续使用现有 `categoryId` 分类规则。支出必须选择小类，收入选择单级分类。 |
| 重复周期 | 每 N 天、每 N 周、每 N 月、每 N 年；默认“每 1 月”。 |
| 开始日期与入账时间 | 必填，组成周期锚点 `startAt`。 |
| 入账日 | 不单独存储；月/年周期从 `startAt` 的日和时间推导。例如开始时间 `2026-04-15 17:04`，即每月 15 日 17:04。 |
| 结束方式 | 永不结束，或指定结束日期。 |
| 账户 | 首期可选，复用现有 `accounts.id`；未选择时为 `NULL`，详情显示“无账户”。 |
| 备注 | 可选，生成流水时写入 `transactions.note`。 |
| 编辑 / 结束 / 删除 | 支持。结束只停止未来生成；已生成流水不删除。删除规则采用归档，保留审计与历史关联。 |

首期不做：借贷、转账、多人分摊、商家、标签、报销、周期规则批量导入、复杂工作日规则（例如“每月最后一个工作日”）。界面上这些位置不应伪造为已可用功能。

### 1.2 规则不是流水

```text
周期规则：每月 15 日 17:04，支出 2,800 元，分类“住宿房租”
       ↓ 到期时服务端物化
生成流水：2026-09-15 17:04，支出 2,800 元，来源 recurring
```

生成后流水仍是当前 `transactions` 表中的普通流水，因此首页、日历、报表、编辑流水都能自然复用；周期账管理只负责管理未来的生成规则和查看该规则已生成的流水。

## 2. 数据模型

### 2.1 新表：`recurring_entries`

每行表示一个周期规则。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | UUID PK | 周期规则 ID。 |
| `book_id` | UUID FK | 所属账本。 |
| `account_id` | UUID FK，可空 | 付款/收款账户。 |
| `category_id` | UUID FK | 收支分类；创建和更新时复用分类层级校验。 |
| `transaction_type` | text | `expense` 或 `income`，首期不支持 `transfer`。 |
| `amount_cents` | bigint | 金额，单位分。 |
| `currency` | text | 默认 `CNY`。 |
| `note` | text，可空 | 周期备注。 |
| `interval_count` | integer | 间隔数，必须大于 0；例如每 2 月为 `2`。 |
| `interval_unit` | text | `day` / `week` / `month` / `year`。 |
| `start_at` | timestamptz | 第一次计划入账时间，同时是重复锚点。 |
| `next_run_at` | timestamptz | 下一次待生成流水的时间，便于列表和到期查询。 |
| `end_at` | timestamptz，可空 | 最后允许生成的计划时间；为空表示永不结束。 |
| `status` | text | `active` / `ended` / `archived`。 |
| `ended_at` | timestamptz，可空 | 用户主动结束的时间。 |
| `created_by` | text FK | 创建规则的用户。 |
| `created_at` / `updated_at` | timestamptz | 审计字段。 |
| `archived_at` | timestamptz，可空 | 删除/归档时间。 |

建议索引：

```text
recurring_entries(book_id, status, next_run_at)
recurring_entries(book_id, archived_at)
```

### 2.2 扩展现有 `transactions` 表

新增以下字段，使生成流水与来源规则可追溯：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `recurring_entry_id` | UUID FK，可空 | 指向生成它的周期规则；手动流水为空。 |
| `recurrence_scheduled_for` | timestamptz，可空 | 该笔流水原计划生成的时间，不能随着用户编辑 `occurred_at` 被覆盖。 |

新增唯一索引：

```text
UNIQUE (recurring_entry_id, recurrence_scheduled_for)
WHERE recurring_entry_id IS NOT NULL
```

这是防重的最后一道保护：即使用户同时打开多个页面、Cron 重试、API 重复请求，同一个规则同一个计划时间最多只会生成一笔流水。

### 2.3 不新增单独的“生成记录表”

首期无需额外 `recurring_entry_runs` 表；`transactions.recurring_entry_id + recurrence_scheduled_for` 已经同时承担“已生成记录”和“实际流水”两种职责。未来若要记录失败重试、通知投递等运行日志，再新增运行表。

## 3. 重复周期与日期计算

### 3.1 UI 选择

参照截图的底部滚轮，第一版在 Web 中可用更易测试的分段控件或两个下拉框实现，语义保持一致：

```text
每 [1] [月]
每 [2] [周]
每 [3] [天]
每 [1] [年]
```

允许范围：`intervalCount = 1..99`，单位为天、周、月、年。

### 3.2 推荐计算规则

所有业务时间以 `Asia/Shanghai` 显示和计算，再存储为带时区时间戳。

| 周期 | 计算方式 |
| --- | --- |
| 天 | 从上一个计划时间加 N 个自然日，保留时分。 |
| 周 | 从上一个计划时间加 N × 7 个自然日，保留星期与时分。 |
| 月 | 保持开始日期的“目标日”；目标日超过当月天数时，生成在该月最后一天。例：1 月 31 日按月重复，2 月生成在 2 月 28/29 日，3 月恢复为 31 日。 |
| 年 | 保持月、日、时分；2 月 29 日在非闰年生成于 2 月 28 日。 |

`startAt` 必须大于或等于创建时刻前允许的最小范围。首期建议允许补建过去规则，但最多补生成最近 12 个月的到期流水；超过范围提示用户使用导入或手动记账，避免一次创建产生大量历史流水。

## 4. 生成机制：可靠且幂等

### 4.1 双通道触发

不能依赖浏览器一直打开，因此采用双通道：

```text
Vercel Cron（每小时） ─┐
                       ├─> POST /api/internal/recurring/run
用户登录 / 打开首页 ───┘       └─> 生成当前账本已到期但未生成的周期流水
```

- **Cron 是主通道**：保证用户不打开应用时，到期流水也会生成。
- **用户请求补偿是兜底**：Cron 延迟、部署暂停或本地开发时，打开首页仍会补齐已到期流水。
- 内部 Cron 路由必须要求 `Authorization: Bearer ${CRON_SECRET}`；`CRON_SECRET` 仅设置在 Vercel，不暴露到浏览器。
- 开发阶段不必配置 Cron：访问账本 API 时调用当前用户账本的补偿函数即可测试。

### 4.2 单个规则的生成算法

```text
输入：规则的 next_run_at、status、end_at、当前时间 now

1. 仅选 status = active、archived_at IS NULL、next_run_at <= now 的规则。
2. 在数据库事务中锁定当前规则，重新读取 next_run_at，避免并发重复处理。
3. 只要 next_run_at <= now 且 next_run_at <= end_at（或 end_at 为空）：
   a. 插入 transactions：
      - source = recurring
      - recurring_entry_id = 当前规则 ID
      - recurrence_scheduled_for = 当前 next_run_at
      - occurred_at = 当前 next_run_at
      - 复制分类、账户、金额、类型、备注、创建人
   b. 依赖唯一索引处理重复插入；冲突时读取既有流水并继续。
   c. 按周期计算下一个计划时间。
4. 若下一个计划时间超过 end_at：
   - 将规则 status 改为 ended；
   - 保留最后生成的流水。
   否则更新 next_run_at。
5. 事务提交。
```

生成函数应限定单次每条规则最多补 24 次，防止异常旧规则一次占满请求。超过时记录日志，下一轮继续补齐。

### 4.3 编辑规则后的影响范围

| 操作 | 已生成流水 | 尚未生成的未来流水 |
| --- | --- | --- |
| 改金额、分类、账户、备注 | 不修改 | 从下一次入账起使用新值。 |
| 改重复周期、开始时间、入账时间 | 不修改 | 重新计算 `next_run_at`；不得重复生成已存在的 `recurrence_scheduled_for`。 |
| 结束 | 不修改 | 立即停止生成。 |
| 归档/删除 | 不修改 | 停止生成，规则不再出现在默认管理列表。 |

首期不允许编辑已生成流水时反向修改规则；“编辑周期账”和“编辑单笔流水”是两个明确不同的操作，避免误改未来账单。

## 5. API 设计

所有公开接口均通过 Better Auth Session 获取用户，并由服务端根据用户获取默认账本；客户端不得传可被信任的 `bookId`。

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/recurring-entries?status=active` | 周期账管理列表。返回分类名称、图标、下一次入账时间、已生成笔数。 |
| `POST` | `/api/recurring-entries` | 新建周期规则。服务端校验分类、账户、金额、周期、开始/结束时间。 |
| `GET` | `/api/recurring-entries/:id` | 周期账详情；含规则、下一次入账、已生成流水列表。 |
| `PATCH` | `/api/recurring-entries/:id` | 编辑未来规则。 |
| `POST` | `/api/recurring-entries/:id/end` | 结束规则，`status = ended`。 |
| `DELETE` | `/api/recurring-entries/:id` | 归档规则，不删除已生成流水。 |
| `POST` | `/api/internal/recurring/run` | Cron 内部入口，仅接受 `CRON_SECRET`。 |

### 5.1 创建/更新请求示例

```ts
{
  transactionType: "expense",
  categoryId: "住宿房租对应的小类 ID",
  accountId: "可选账户 ID 或 null",
  amountCents: 280000,
  note: "马可汇房租2800",
  intervalCount: 1,
  intervalUnit: "month",
  startAt: "2026-09-15T17:04:00+08:00",
  endAt: null
}
```

### 5.2 列表返回示例

```ts
{
  id: "...",
  status: "active",
  transactionType: "expense",
  amountCents: 280000,
  category: { id: "...", name: "住宿房租", icon: "home", color: "#28c5b4" },
  note: "马可汇房租2800",
  interval: { count: 1, unit: "month", label: "每月" },
  nextRunAt: "2026-09-15T17:04:00+08:00",
  generatedCount: 4
}
```

## 6. 前端交互与页面

### 6.1 周期账管理列表

对应参考图“周期账管理”。

- 从首页“周期账”快捷入口进入。
- 默认展示 `active` 规则；底部“已终止”可切换查看 `ended` 规则。
- 每一行展示：分类图标、分类名、备注、下次计划时间、周期文本、账户/成员简要信息和金额。
- 金额颜色沿用现有逻辑：支出深色负号，收入橙色正号。
- 底部固定“+ 添加”按钮。
- 点击某行进入详情。

### 6.2 新建 / 编辑周期账

参考“编辑周期账”，但结合当前项目已实现能力做减法：

| 区块 | 字段与行为 |
| --- | --- |
| 基础信息 | 类型（收入/支出）、分类、金额、账户、备注。类型与分类复用现有 `CategoryPicker`。 |
| 周期设置 | 开始日期、重复周期、入账时间、结束日期。 |
| 结束日期 | “永不结束”或选择一个日期；结束日期不得早于开始日期。 |
| 保存 | 保存中状态；成功返回详情或管理列表。 |

不展示尚未实现的成员、商家、标签、报销选项，避免界面与实际能力不一致。

### 6.3 重复周期选择器

参考“选择重复周期”底部面板。

- 移动端：底部抽屉，标题“选择重复周期”。
- 第一列为数字 `1–99`，第二列为 `天 / 周 / 月 / 年`。
- 确认后显示为：`每天`、`每周`、`每月`、`每年`，或 `每 2 周`、`每 3 月`。
- 桌面端可替换为数字输入框 + 单位分段选择，保证键盘可访问性。

### 6.4 周期账详情

对应参考“周期账详情”。

展示：

- 分类、金额、账户、备注；
- 开始时间、重复周期、入账日、入账时间、结束时间、下次入账；
- “生成账单 N 笔”，进入该规则生成的流水筛选列表；
- 底部操作：结束、编辑、删除（归档）。

对于已结束规则：隐藏“下次入账”，显示结束时间；底部不再显示“结束”，保留“编辑（仅备注等元信息）/ 归档”。

## 8. Migration 与部署步骤

1. 修改 Drizzle schema，生成新的 migration；不改动已经应用的 `0000`、`0001`、`0002`。
2. 审查新增外键、索引和 `transactions` 唯一约束。
3. 本地执行 `npm run db:migrate`，验证 Preview Neon 表结构。
4. 完成 API 和前端后执行 `npm run build`。
5. 在 Preview 环境配置：

```env
CRON_SECRET="高强度随机字符串，仅服务端使用"
```

6. 配置 Vercel Cron 请求 `/api/internal/recurring/run`；路由验证授权头后才执行。
7. 在 Preview 完成端到端回归，最后再将规则部署到生产 Neon 分支。

## 9. 验收清单

### 创建与选择

- 能创建“每月 15 日 17:04，住宿房租，2,800 元”的支出周期账；
- 支出无法选择大类直接保存，收入无法选择支出小类；
- 可选择每天、每周、每月、每年，以及 N > 1 的间隔；
- 收入界面和分类图标保持橙色，支出保持青绿色。

### 到期与防重

- `next_run_at` 到期后能生成一笔 `source = recurring` 的真实流水；
- 连续调用生成 API 两次，同一计划时间仍只有一笔流水；
- 停止 Cron 后再打开首页，当前用户到期的周期账会补齐；
- 一个规则积压多个周期时，按计划时间顺序补齐，单次最多 24 笔；
- 月末、闰年日期按第 3.2 节规则正确计算。

### 管理与历史

- 编辑金额/分类后，不影响已生成流水，只影响未来流水；
- 结束后不再生成未来流水，历史流水可继续查看；
- 归档规则后不在默认列表展示，历史流水及“已生成账单”仍可访问；
- 用户无法读取、编辑、结束或归档其他用户账本的周期规则。

## 10. 实施优先级

1. **P0：数据模型和幂等生成器**——这是周期账正确性的基础，先完成并写测试。
2. **P1：创建、管理列表、详情、结束/归档**——完成用户可用闭环。
3. **P2：Vercel Cron 与 Preview 验证**——保证用户不打开页面时也会按期生成。
4. **P3：规则生成流水筛选、更多结束条件、工作日规则、提醒通知**。

## 11. 关键决策

- 周期账不是前端定时器：最终生成必须在 Next.js 服务端和 Neon 事务中完成。
- 规则变化不回写历史：保证用户已经确认的流水不会被未来规则修改。
- 使用 `recurring_entry_id + recurrence_scheduled_for` 的唯一约束防重，而不是只依赖 `next_run_at` 判断。
- 首期重复周期以“每 N 天/周/月/年”为准，覆盖截图“每 1 月”的需求，同时控制实现复杂度。
- 先完成稳定入账，再扩展提醒、工作日、多人分摊等增强功能。
