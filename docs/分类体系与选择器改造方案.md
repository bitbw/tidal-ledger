# 分类体系与选择器改造方案

> 版本：v1.0｜日期：2026-08-27  
> 依据：[挖财分类清单-截图整理.md](./挖财分类清单-截图整理.md)、当前 `preview` 分支代码与现有 Neon/Drizzle 数据结构。  
> 目标：把当前的扁平分类改成“支出两级、收入单级”，并实现常用分类、全部分类、分类新增与管理闭环。

## 1. 完成后的体验

```text
新增 / 编辑流水
  ├─ 支出：展示常用小类 + “全部”
  │    └─ 全部 → 支出大类列表 → 点击大类 → 小类列表 → 选中小类并返回记账面板
  ├─ 收入：展示常用收入分类 + “全部”
  │    └─ 全部 → 收入分类列表 → 选中分类并返回记账面板
  └─ 选择器底部：新增分类 | 管理
       ├─ 新增：进入新增页面，可选收入/支出；支出小类必须选择所属大类
       └─ 管理：进入分类管理页；收入管理单级，支出管理大类及其小类
```

流水、日历、最近流水、报表和编辑页展示时统一显示：**小类名称**；需要上下文的位置（例如报表筛选、管理页）显示 **大类 / 小类**。

## 2. 当前代码的差距与关键约束

当前 `src/features/ledger/schema.ts` 中的 `categories` 只有 `name`、`kind`、`icon`、`color`、`sortOrder`，属于扁平分类。`createLedgerTransaction` 和 `updateLedgerTransaction` 通过 `(bookId, categoryName)` 查分类。

这不能直接支持目标设计，原因如下：

- 支出需要父子关系，当前表没有 `parent_id`。
- 小类可以重名，例如“保险”“其他”；按名称查找会选错类别，必须由前端提交 `categoryId`。
- 删除已被历史流水引用的分类会破坏展示；需要归档，不应物理删除。
- 当前 `GET /api/ledger` 未返回分类树，记账面板仍有本地硬编码分类。

## 3. 数据模型改造

### 3.1 `categories` 表扩展

新增字段：

| 字段 | 类型 / 默认值 | 用途 |
| --- | --- | --- |
| `parent_id` | `uuid`，可空，自关联 `categories.id` | 支出小类指向支出大类；支出大类与全部收入分类为 `NULL`。 |
| `is_system` | `boolean`，默认 `false` | 标识预置分类；首期仅用于区分初始化数据和用户分类，不限制用户编辑。 |
| `archived_at` | `timestamptz`，可空 | 软删除/停用。已有流水仍保留原 `category_id`，但新建时不再展示。 |
| `updated_at` | `timestamptz`，默认当前时间 | 分类编辑审计。 |

建议索引与约束：

- 索引：`categories(book_id, kind, parent_id, sort_order)`，服务常用分类树读取和排序。
- 索引：`categories(book_id, archived_at)`，排除归档分类。
- 服务端校验而不是仅靠 UI：
  - `expense` 的根节点为大类；子节点必须也是 `expense`；子节点不能再有子节点。
  - `income` 不允许 `parent_id`。
  - 流水中的 `category_id`：支出必须指向支出小类；收入必须指向收入根分类。

### 3.2 数据迁移与初始化

1. 修改 Drizzle schema，生成一个新的 migration；**不修改**已应用的 `0000`、`0001` migration。
2. 新用户首次创建账本时，写入：
   - `expense` 支出大类及已整理小类；
   - `income` 28 个单级分类；
   - 图标和颜色使用合理的 Lucide 图标映射，颜色遵循支出青绿、收入橙色的视觉基调。
3. 已有用户数据迁移策略：
   - 旧分类名称与新预置分类同名时，保留旧分类 ID，并按映射补充其父大类；例如“早餐/午餐/晚餐/饮料水果”归到“餐饮”。
   - 无法映射或用户自建的旧分类，创建/保留为根级 `expense` 或 `income` 分类，标记为“待整理”；不可静默猜测父级。
   - 因为当前流水已保存 `category_id`，迁移时不要重写历史流水；只调整分类表即可保留历史关联。

### 3.3 流水 API 契约调整

将请求字段由 `categoryName` 改为 `categoryId`：

```ts
POST /api/ledger
PATCH /api/ledger

{
  transactionType: "expense" | "income",
  amountCents: number,
  categoryId: string,
  note?: string
}
```

服务端必须按以下顺序校验：登录用户 → 默认账本/成员身份 → 分类属于该账本且未归档 → 分类类型匹配流水类型 → 支出分类必须是小类、收入分类必须是根级 → 写入流水。

`GET /api/ledger` 增加 `categories` 字段，至少返回：

```ts
{
  id, name, kind, parentId, icon, color, sortOrder, archivedAt
}
```

流水读取结果也增加 `categoryId`、`categoryName`、`parentCategoryName`，避免编辑页依赖名称反查。

## 4. 页面与组件设计

### 4.1 记账面板：常用分类区

沿用当前首页的新增/编辑面板和金额键盘，替换原有扁平分类按钮：

- 支出：优先显示最近使用的 8 个支出小类；数据不足时用推荐项补齐（早餐、午餐、晚餐、打车、购物等）。
- 收入：优先显示最近使用的 8 个收入分类；不足时用工资薪水、奖金、兼职外快、红包等补齐。
- 最后一格固定为“全部”（省略号图标）。
- 点击常用小类立即选中；点击“全部”打开分类选择抽屉。
- 新增/编辑共用一个 `CategoryPicker`，编辑时需根据流水现有 `categoryId` 正确回显。

常用排序不需要第一版新增表：可从当前账本最近 90 天流水按使用次数、最近一次使用时间计算；同分再按分类 `sortOrder`。未来如需用户手动固定常用项，再新增 `category_preferences` 表。

### 4.2 全部分类抽屉

移动端使用底部抽屉，布局与参考图一致：

- 标题为“选择分类”；提供关闭、搜索、排序入口（排序第一版可先不做功能）。
- **支出**：显示支出大类行；点击行进入该大类的小类列表。若某个用户大类暂无小类，显示空状态与“新增小类”。
- **收入**：直接显示收入分类列表，无第二层。
- 底部固定操作区：“+ 新增分类”和“管理”。
- 搜索范围覆盖当前收支类型下的大类和小类；命中小类时展示 `大类 / 小类`，点击后直接选中。

### 4.3 新增分类页面

参照截图的“新增类别”样式实现独立页面/全屏抽屉：

- 字段：收支类型、名称、所属大类、颜色、图标、保存。
- 新建支出大类：所属大类为“无”。
- 新建支出小类：所属大类必填，只能选择支出大类。
- 新建收入分类：所属大类固定为“无”，不展示二级选择。
- 名称做 trim、长度校验和同级重名校验；同一账本、同一父级、同一类型下不得重复。
- 成功后返回调用入口：从记账页进入时自动选中新分类；从管理页进入时回到对应分类列表。

### 4.4 分类管理页面

入口为选择器底部的“管理”。

| 模块 | 行为 |
| --- | --- |
| 收支切换 | 支出 / 收入分段控件。 |
| 支出列表 | 展示大类；点击大类进入小类管理列表。 |
| 收入列表 | 直接展示单级收入分类。 |
| 编辑 | 点击任一分类进入编辑页，可改名称、图标、颜色、排序。 |
| 新增 | 支出顶层新增大类；大类详情新增小类；收入新增收入分类。 |
| 停用 | 对没有流水的分类可提示删除；有流水时只提供“归档”，历史流水仍显示该分类。 |
| 排序 | 第一版提供上移/下移或拖动排序，落库至 `sort_order`。 |

## 5. 后端接口拆分

在现有 `/api/ledger` 之外新增分类 Route Handler：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `GET` | `/api/categories?kind=expense` | 读取当前用户账本的分类树；默认排除归档。 |
| `POST` | `/api/categories` | 新增收入分类、支出大类或支出小类。 |
| `PATCH` | `/api/categories/:id` | 改名称、图标、颜色、排序或归档状态。 |
| `POST` | `/api/categories/:id/archive` | 归档分类；服务端检查归档大类时必须同时处理/阻止其有效小类。 |

所有接口都通过 Better Auth Session 获取用户身份，再在服务端取得该用户默认账本；请求体不得携带可被信任的 `bookId`。所有分类 ID 必须额外校验属于当前账本。

## 7. 实施顺序与验收

### 阶段 A：数据库与服务端

1. 扩展 Drizzle `categories` schema，生成 migration。
2. 实现新用户的预置分类初始化，并完成已有分类的安全映射 migration。
3. 把流水新增/编辑的分类参数切为 `categoryId`，保留 `categoryName` 仅作展示返回值。
4. 完成分类树读取和分类 CRUD API。

验收：在 Neon Preview 数据库中，支出大类/小类和收入单级分类均能正确读取；不同大类的同名小类不会互相串写；不能使用其他账本的分类创建或更新流水。

### 阶段 B：记账选择器

1. 接入常用分类和“全部”抽屉。
2. 实现支出两级选择和收入单级选择。
3. 接入新增分类、管理入口及返回后自动选中。
4. 改造新增、编辑、最近流水和日历流水的分类回显。

验收：支出必须先选到小类才能保存；收入可直接选择并保存；编辑旧流水后分类、金额和备注均正确更新；手机/桌面键盘输入金额和保存加载状态不回归。

### 阶段 C：管理、迁移与回归

1. 完成编辑、排序、归档与空分类处理。
2. 为历史旧分类提供“待整理”迁移提示或管理入口。
3. 回归首页、日历、流水列表、报表、导入预览。

验收：归档分类不再出现在新增选择器中，但历史流水、日历和报表仍可正常展示；构建通过，且 Preview 环境完成新建、编辑、归档、刷新后的端到端验证。

## 8. 明确不在本次改造中做的内容

- 转账、借贷、周期账、预算的专用分类体系；本次只改收入与支出。
- 图标上传、自定义 SVG；第一版使用 `lucide-react` 的白名单图标。
- 原始账单导入的自动二级分类；导入确认入库功能尚未完成，后续接入时直接使用同一 `categoryId`。
- 因收入分类较少而强行增加收入二级分类；用户已明确收入保持单级。

## 9. 风险与决策

- **不能继续按名称写入分类。** 这是本改造的强制变更，否则重名小类会造成数据错误。
- **不能物理删除被流水引用的分类。** 使用 `archived_at` 可兼顾历史准确性与选择器整洁。
- **首期不要把所有“常用”写死。** 采用真实使用频次和最近使用时间，用户新建分类后也能自然出现在常用区。
- **当前保留的支出大类均已有小类清单。** 初始化时按分类清单预置；后续仍允许用户新增自定义大类和小类。
