# 潮汐账本 Web 应用：Neon 整体实现方案

> 版本：v2.0｜更新日期：2026-08-27  
> 当前状态：Neon `preview1` 分支已完成数据库迁移；邮箱密码注册、登录和手动记账已在本地联调通过。  
> 定位：移动优先的中文个人记账 Web 应用。先完成“注册 → 记账 → 跨设备数据保存”的可靠闭环，再逐步完善导入、预算和报表。

## 1. 目标与边界

产品的核心目标是让用户能快速记录收支、在多台设备访问同一份账本，并安全导入自己的微信/支付宝账单。

首版坚持以下原则：

- 移动优先：手机端优先保障快速记账、金额键盘和最近流水；桌面端提高信息密度。
- 云端优先，最小化上传：确认后的结构化流水存入 Neon；原始账单默认仅在浏览器本地解析。
- 先预览，后入账：批量导入必须展示分类、账户、重复项和异常项。
- 金额可追溯：所有金额使用分（`amount_cents`）存储，报表应能追溯至流水。
- 分支隔离：开发、Preview 和生产环境必须使用不同的 Neon 分支和连接串。

首版不做代登录、抓取微信/支付宝账号、保存支付密码或 Cookie，也不把 AI 自动记账作为前置能力。

## 3. 技术架构

| 层级 | 当前选型 | 职责 |
|---|---|---|
| Web 框架 | Next.js 16.3.3 + React 19 + TypeScript | App Router、页面与 API Route Handlers。 |
| UI | Tailwind CSS + shadcn/ui + 自定义组件 | 移动优先界面、表单和基础交互。 |
| 认证 | Better Auth 1.7.2 | 邮箱密码注册、登录、Cookie/Session 和认证 API。 |
| 数据库 | Neon Postgres | 用户、会话、账本、流水、预算与导入数据。 |
| ORM / migration | Drizzle ORM + Drizzle Kit | TypeScript schema、SQL migration 和数据库访问。 |
| 数据库驱动 | `pg` + `@vercel/functions` | Node.js 连接池，并适配 Vercel Serverless 生命周期。 |
| 部署 | Vercel | Git 分支部署、Preview、Production 和环境变量。 |
| 文件解析 | Papa Parse、read-excel-file、fflate | 在浏览器中解析 CSV、XLSX、ZIP 账单文件。 |

```text
浏览器
  ├─ Next.js 页面：首页、记账面板、导入预览、登录/注册
  ├─ Better Auth Client：发起注册、登录、读取 Session
  └─ 本地账单解析：CSV / XLSX / ZIP，不上传原始文件
        ↓ HTTPS
Next.js Route Handlers
  ├─ /api/auth/[...all]：Better Auth
  └─ /api/ledger：已登录用户的账本读取与手动记账
        ↓
Drizzle ORM + pg Pool
        ↓
Neon Postgres
  ├─ Better Auth 表：user、account、session、verification
  └─ 账本表：books、book_members、accounts、categories、transactions、budgets、import_batches、import_rows
```

## 4. 环境与分支策略

当前已验证的组合是 Git `preview` 分支配合 Neon `preview1` 数据库分支。连接串只能放在本地 `.env.local` 或 Vercel 环境变量，禁止提交到 Git、文档或聊天记录。

| 环境 | Git / 部署 | Neon 分支 | 数据用途 |
|---|---|---|---|
| Local | 本机 `npm run dev` | 当前使用 `preview1` 进行联调；长期建议独立 `development` | 开发和个人测试数据。 |
| Preview | `preview` 分支 / Vercel Preview | `preview1` 或未来的 `preview-*` | 部署前验证，禁止放真实敏感账单。 |
| Production | `main` 分支 / Vercel Production | Neon `main` | 正式用户数据。 |

本地最小环境变量：

```env
DATABASE_URL="postgresql://...-pooler.../neondb?sslmode=require"
BETTER_AUTH_SECRET="至少 32 个随机字符"
BETTER_AUTH_BASE_URL="http://localhost:5001"
```

Vercel 的 Preview 与 Production 都需要分别设置：

```env
DATABASE_URL=
BETTER_AUTH_SECRET=
BETTER_AUTH_BASE_URL=
```

其中 `DATABASE_URL` 必须指向对应环境的 Neon 分支；`BETTER_AUTH_BASE_URL` 是应用访问地址，不是数据库地址。当前认证配置使用固定 base URL；部署到会变化的 Vercel Preview URL 前，应将其改为允许受控 Preview 域名的动态主机白名单，或为 `preview` 分支配置稳定访问域名。

## 5. 认证与权限模型

### 5.1 Better Auth

项目不使用 Supabase Auth，也不需要在 Neon 中配置浏览器认证回调。Neon 仅提供 PostgreSQL；Better Auth 负责认证流程，并把认证数据写入 Neon。

当前启用方式：

```text
邮箱 + 密码注册
  → Better Auth /api/auth/sign-up/email
  → user、account 写入 Neon
  → 登录后创建 session
  → Cookie 携带 Session 访问 /api/ledger
```

当前的 `account` 表必须包含 `issuer` 字段。Better Auth 1.7 以 `(issuer, account_id)` 识别账号；缺失该字段会导致注册返回 500。

后续可在 Better Auth 上接入 OAuth、手机号 OTP、邮箱验证码、Passkey 或两步验证；这些能力需要额外配置对应身份提供商或短信服务商，Neon 仍只负责存储数据。

### 5.2 账本权限

数据模型已包含 `book_members` 与 `owner` / `editor` / `viewer` 角色，为共享账本预留空间。当前应用仅实现单用户默认账本：服务端通过 Better Auth Session 获取用户 ID，再查询/创建该用户的账本。

本项目不再使用 Supabase RLS。当前权限边界由 Next.js 服务端 API 与 Drizzle 查询实现；在开放共享账本前，必须补齐服务端的成员校验、角色授权、越权测试和审计规则，不能只依赖前端隐藏按钮。

## 6. 数据模型

### 6.1 认证表

```text
user            用户资料
account         登录凭据与第三方账号绑定，包含 issuer
session         会话
verification    验证令牌
```

### 6.2 账本领域表

```text
books           账本
book_members    账本成员及角色
accounts        资金账户（微信、支付宝、现金等）
categories      收入/支出分类
transactions    标准化流水
budgets         月度和分类预算
import_batches  导入批次
import_rows     导入行结果与元数据
```

`transactions` 的关键字段：

```text
id, book_id, account_id, category_id
transaction_type       expense | income | transfer
amount_cents           整数，单位为分
currency               默认 CNY
occurred_at, merchant_name, note
source                 manual | wechat | alipay | csv
external_transaction_id, source_row_hash, import_batch_id
transfer_pair_id, created_by
created_at, updated_at, deleted_at
```

金额一律存储为分，禁止使用浮点数。例如 `63.45 元` 保存为 `6345`。

已实现索引：

- `transactions(book_id, occurred_at)`：最近流水和后续月历查询；
- `transactions(book_id, source, external_transaction_id)`：平台交易号去重基础；
- `book_members(book_id, user_id)`：成员唯一性；
- `account(issuer, account_id)`：Better Auth 账号唯一性。

## 7. 已实现接口与交互

|---|---|---|
| `POST /api/auth/sign-up/email` | 已验证 | 邮箱密码注册。 |

| `GET /api/ledger` | 已验证 | 获取当前用户默认账本、账户与最近 300 笔未删除流水；首次访问初始化默认账本。 |

## 8. 账单导入方案

现有 `src/features/importers/parse-statement.ts` 已支持在浏览器端解析 CSV、XLSX 和 ZIP，并生成预览。原始账单默认不上传。

目标流程：

```text
用户从微信/支付宝官方入口导出账单
  → 浏览器本地解析与来源识别
  → 标准化日期、金额、收支、商户和交易号
  → 预览、分类、目标账户选择、重复提示
  → 用户确认
  → 服务端单事务创建 import_batches、transactions、import_rows
  → 展示结果；支持按批次撤销
```

当前缺口是“确认后写库”。实现时必须：

- 在服务端重新校验解析后的请求数据，不能信任浏览器传入的分类、金额和账本 ID；
- 先以 `(book_id, source, external_transaction_id)` 去重，再处理无交易号的相似记录；
- 将一批导入包裹在单个数据库事务中；
- 支持 `import_batch_id` 维度的软删除/撤销；
- 保持原始文件不入库，除非未来提供用户明确开启的备份能力。

## 9. 数据库变更工作流

不要修改已经应用到任一环境的历史 migration SQL。标准流程：

```text
修改 Drizzle schema
  → npm run db:generate
  → 审查 drizzle/ 下新 SQL 和 snapshot
  → 确认 .env.local 指向目标 Neon 分支
  → npm run db:migrate
  → npm run build
  → 注册、登录和业务回归验证
```

Better Auth schema 生成后也必须审查 diff。当前 `auth:generate` 脚本引用 `@latest`，在升级 Better Auth 或重新生成认证 schema 前，应先确认 CLI 输出与项目锁定的运行时版本兼容，再生成并创建 Drizzle migration。

## 12. 最终结论

当前项目已经从 Supabase 架构迁移为：

```text
Next.js + Vercel
  + Better Auth（认证与 Session）
  + Drizzle ORM（schema 与 migration）
  + Neon Postgres（认证数据与账本数据）
```

已完成的最小闭环是：

```text
注册 → 登录 → 自动创建默认账本 → 手动记账 → Neon 持久化 → 刷新后读取
```

下一步的最高优先级不是继续扩展页面，而是将这条已验证链路部署到 Vercel Preview 并再次验证；随后依次完成真实报表/预算、导入确认入库和生产环境隔离。
